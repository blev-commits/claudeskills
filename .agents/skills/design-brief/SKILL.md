# Design Brief

Turn a rough feature description into a clear problem definition before any design work starts.

## Brief structure

**Feature name**
One line. If unnamed, give it a working title.

**The problem**
2 to 3 sentences. What is the user currently unable to do, or doing badly? No solution language here.

**Who it's for**
The primary user and their context. Note secondary users separately if relevant.

**What success looks like**
Frame in user behavior, not metrics. "Users can complete X without contacting support" beats "increase conversion rate."

**Scope**
What is in scope for this design pass. What is explicitly out. This prevents scope creep.

**Constraints**
Technical limitations, platform requirements, timeline, design system boundaries, legal or accessibility requirements.

**Open questions**
Anything that needs an answer before or during design. Write these as actual questions. This is the most important section.

**References**
Existing designs, tickets, research, or competitor patterns worth reviewing before starting.

---

## How to write it

Extract what you know from what the user provides. Where information is missing, make a reasonable assumption and mark it clearly with [Assumed]. Surface the 3 to 5 most important open questions. Keep the whole brief to one page. If it is getting longer, you are documenting a solution, not a problem.
